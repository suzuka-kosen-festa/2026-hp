# MAPは「何がどこにあるか」と次の行動を伝える

作成日: 2026-10-02
状態: 2026-10-02、ユーザーが設計書を承認。見出しの誘い文句を削除する修正を反映済み。

MAPの目的は、来場者が気になる場所を発見し、場所を把握して、そのエリアの情報へ進めること。工作・切り貼りの楽しさを残しながら、名称、位置、操作結果が読み取れる案内にする。掲載する7エリアは変更しない。

この文書では情報の優先順位、画面の役割、遷移、未確定情報の扱い、レビュー条件を定める。具体的な構図は編集用Figmaで人間と調整する。サイトコードの実装と公開操作は今回行わない。

## 1. MAPは場所を案内し、時間表はタイムテーブルに任せる

最新の正は `docs/requirements.md`、表現の基準は `docs/design-system.md` とポスター。今回の会話で、MAPの中心を「何がどこにあるか」「気になる場所の情報へ迷わず進める」と確認した。

MAPに新しい時間表や営業時間一覧は追加しない。時間に関する表示は、既存要件にある3ステージの「開催中の企画タイトル」に限る。詳しい開催時間はタイムテーブルで確認する。

主な利用者は地域の来場者、中学生と保護者、在学生の家族。スマホで片手操作する当日利用と、PCで会場を把握する事前利用を想定する。

GPS現在地、経路検索、推定徒歩時間、混雑情報、個別ブースのピン、フリーテキスト検索、スタンプ収集は対象外。情報が確定したという理由だけで、これらの機能を追加しない。

## 2. 地図で位置関係をつかみ、一覧でエリアを選べる

地図中心の構成は会場の関係を伝えやすいが、小さな文字や図形を読み取る負担がある。一覧中心の構成は名称を探しやすい一方、建物の位置関係が伝わりにくい。地図と7エリア一覧を併設し、どちらからでも同じ情報へ進める構成を採用する。

スマホの全体画面は、次の情報順でFigmaを調整する。余白、図の向き、カード配置の具体値はFigmaで確認して決める。

1. 「会場マップ」の見出し。キャッチコピーは置かず、別の誘い文句にも差し替えない。
2. 全体地図。確認済みの入口、建物、エリアの位置関係を示す。
3. 「エリアを選ぶ」の見出しと7エリア一覧。

番号は地図と一覧を結びつける識別子として使う。番号だけで場所を選ばせず、エリア名も添える。一覧には「番号・エリア名・場所・次に見られる情報」を載せる。装飾のために名称や場所を画像に埋め込まない。

地図の向きと建物の位置関係は維持する。スマホでは画面幅に収め、ピンチズームやパンを必須にしない。PCも同じ情報と行き先を使い、レイアウトだけをFigmaで調整する。

位置が未確定のエリアは一覧に残し、地図上に仮の位置を置かない。仮置きの部品はFigmaの制作領域に分離し、来場者向けの画面では実際の位置に見せない。

## 3. 行き先が決まっているエリアは直接案内する

地図と一覧の同じエリアは、同じ行き先、同じ準備状態を持つ。全体地図で選んだあとに、もう一度同じ名前のボタンを押す確認画面は必須にしない。タップ時のハイライトは短くし、演出の完了を待たないと進めない作りにしない。

| 番号 | エリア | 場所 | 準備が整ったときの行き先 | 一覧の操作文言 |
|---|---|---|---|---|
| ① | LiveStage | 第一体育館 | タイムテーブルの該当ステージ | ステージの時間を見る |
| ② | MainStage | 屋外 | タイムテーブルの該当ステージ | ステージの時間を見る |
| ③ | 飲食バザー | 屋外 | 飲食バザーの詳細配置 | 店舗の配置を見る |
| ④ | 展示・レク | 教室棟 | 校内の階別配置 | 校内の配置を見る |
| ⑤ | ゲームイベント | 教室棟 | ブース一覧の出店タブ・該当セクション | ゲームイベントの出店情報を見る |
| ⑥ | SubStage | 屋外 | タイムテーブルの該当ステージ | ステージの時間を見る |
| ⑦ | 学科展示 | 第二体育館 | ブース一覧の学科展示タブ | 学科展示を見る |

③④は配置データが揃うまで、既存要件どおりタップ先を準備中の案内にする。この状態では操作文言を「配置は準備中」に変え、完成済みの配置図が見られると期待させない。案内画面には確認済みのエリア名と場所を残し、「会場全体に戻る」を用意する。詳細配置へ進むように見える無効なボタンは置かない。

①②⑥は該当ステージ、⑤⑦は該当するタブ・セクションが見える状態に着地させる。無関係な一覧の先頭へ送って、利用者に探し直させない。⑤を単に「レク」のタグで代用すると他の企画を混ぜる可能性があるため、対象エリアとの対応を確認してから接続する。

ブラウザの戻る操作では、MAPの選択階とスクロール位置を復元する。画面内の「会場全体に戻る」でも全体へ戻れるようにする。復元状態がなければ通常の全体画面を表示する。

## 4. 校内では階と教室表記を見失わせない

校内画面は「展示・レク」「現在の階」「階切替」「校内図」「その階の企画一覧」の順で整理する。教室ごとに押す操作は必須にせず、図を読み取りにくい人も一覧から企画を探せるようにする。

承認済みの前年のC科棟・南棟、1〜3Fの形を使う。前年の配色やデザイン、企画番号・割り当ては引き継がない。階を切り替えても棟名と図の向きを揃え、選択中の階は文字と枠でも示す。

配置確定後、一覧は企画名、棟、階、教室または区画、企画詳細へのリンクを持つ。図と一覧で教室表記を統一する。必要な参加条件は企画詳細へ渡し、MAP内に長文を複製しない。

配置が未入手の間は「今年の企画と教室の割り当ては調整中です」と明示し、架空の企画や空の教室を「企画なし」と表示しない。1Fの図を複製しただけの2F・3Fは制作領域に置き、来場者向けの階切替に接続しない。詳細図の一般公開は、今年の配置と通行可能な範囲を確認した後に行う。

飲食バザーも同様に、図と店舗一覧で区画表記を揃える。座標未入手の段階では確認済みの位置テキストだけを扱い、配置図上の位置は推定しない。

## 5. 情報の確かさと操作できる範囲を区別する

| 状態 | 表示と動作 |
|---|---|
| エリア名・場所が確定 | 名称と場所を表示する |
| 配置が未確定 | 「配置は準備中」。仮の座標を表示しない |
| 時刻の記載がない | 開催中・終日開催と判定しない |
| 対象の企画データが未登録 | 「企画なし」と断定しない |
| 日時と公開対象が確認できたステージ企画が開催中 | 3ステージの該当エリアに「開催中」と企画タイトルを表示する |
| 会期外、開催中の該当企画なし | 開催中表示を出さない。エリア自体は残す |
| 遷移先ページが未公開 | 完成した情報が見られるように表示せず、既存の公開制御に従う |

開催中の表示はタイムテーブルと同じ開催データを参照し、一般来場者向けの公開対象だけを扱う。中夜祭など通常のタイムテーブルから除外する企画も同じ条件で除外する。端末の日時や更新の不確かさがあるため、開催中表示だけを現地案内の根拠にしない。

入口は「入口」と表示する。現在地を取得しない画面に「現在地」のマーカーは置かない。階段、トイレなどの施設記号は位置と利用条件を確認したものだけを使い、未確認の通路や設備を追加しない。

## 6. コラージュは興味を引き、文字と操作は読みやすくする

建物やバザーを切り抜いた紙の部品として見せ、番号札、テープ、印刷の影を組み合わせる。赤・青・黄と白地、黒い輪郭は既存の世界観に合わせる。色紙の重なりは装飾に使い、建物の位置関係やラベルを隠さない。

本文、棟名、教室名には歪みを掛けない。紙端や装飾は動かしてよいが、地図の操作領域と一覧の読み順は安定させる。テープとチップは不透明にする。

操作領域は44×44 CSS px以上を設計目標とし、隣のエリアと重ならないようにする。数字、名称、枠などを併用し、色だけで対応や選択状態を伝えない。キーボード操作と読み上げでも一覧から同じ情報へ進めるようにする。動きを減らす設定でも、情報と選択状態はすべて表示する。

これらは設計条件であり、アクセシビリティ適合を確認済みという意味ではない。参考: [W3C・操作対象の大きさ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)、[W3C・色の使用](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)。

## 7. 部品とデータを分け、情報の食い違いを防ぐ

編集用Figmaは `USj2vcyNX2syrxtzulfnQ6` を使い、参照用 `yHxFTvhmA7nNsLEk4mGdIG` は読み取りに限定する。建物、バザー、ステージ、番号札、一覧カード、階切替、準備中の案内は再利用できる部品として扱う。画面全体を画像化せず、文字と図形を編集可能に保つ。

Web実装では、番号・名称・場所・遷移先・配置の準備状態をMAP側の一つのエリア定義から取得する。地図と一覧に別々の文言やリンクを持たせない。企画の名称、時刻、参加条件は既存の `entries/` を参照し、MAP専用のコピーを作らない。

役割は、全体地図、エリア一覧、詳細配置、準備中案内、開催中判定、遷移先の対応付けに分ける。紙の見た目の変更が掲載情報や行き先を変えない構造にする。現在の `Entry.location` は自由文を含むため、文字の一部分だけを見て教室や区画を推定しない。

現状の `deepLink.ts` はタブ・タグ・スクロール先を持つが、ステージ指定は持たない。接続方法は実装計画で定め、タイムテーブル担当と調整する。ゲームイベントの対象の対応付けも同様。共通部品やデータスキーマを変更する場合は共同作業ルールに従い、無断で変更・Discord送信はしない。

公開可否は引き続き `site/src/data/release.json` だけで決める。配置が完成したことと、ページを公開することは分ける。

## 8. 「探せる・間違えない・戻れる」をレビューする

まず375px幅で確認し、その後PCを見る。以下は合格条件であり、現時点の検証結果ではない。

| 確認課題 | 合格条件 |
|---|---|
| 第一体育館のLiveStageを探す | 名称と場所が図・一覧で一致し、該当ステージの情報に進める |
| 学科展示を探す | 第二体育館だと分かり、学科展示タブに着地する |
| 展示・レクの別の階を見る | 選択階と図・一覧が一致する。制作中の複製図を完成図として表示しない |
| 飲食バザーの配置が未確定 | 準備中と分かり、仮配置や架空の店舗情報に誘導しない |
| 詳細を見て戻る | 元の階と閲覧位置から探し続けられる |
| 色や地図を頼らず探す | 番号と文字の一覧から同じ情報へ進める |
| 会期外・時刻未定・中夜祭を扱う | 不適切な開催中表示を出さない |

Figmaでは全体、準備中、配置確定後の詳細、階切替、戻る導線を試す。制作中の画面や説明用のサンプルには制作状態を明示し、実データと混同させない。コード化後はリンク先の状態、キーボード操作、文字拡大、動きを減らす設定を実機に近い環境で確認する。座標データ待ちの検査は、データが揃うと自動で有効になる形にする。

賞を狙う品質レビューは、表現の独自性、情報の読み取りやすさ、操作の一貫性、実装品質をそれぞれ確認する。見た目が整っただけで合格にしない。自己レビューは受賞の保証ではなく、実際の利用者による確認も必要になる。

## 9. 未確定の配置を作らず、確認後にFigmaへ反映する

2026-10-02の確認では、編集用Figmaに1Fの試作と、1Fを複製した制作中の2Fがある。3F、階切替、詳細配置の接続は未完成。これらは本番向け完成状態ではない。

今年のバザー・ゲームの正確な位置、教室の割り当て、施設の利用条件は未確認。前年の建物形状を使えるという承認とは切り分ける。データが届くまでは、準備中の案内を完成させる。

次は承認された設計書に沿って、Figma更新の作業計画を作る。全体画面と準備中案内で情報と導線を確かめ、配置データのある範囲だけ詳細図に進める。Figmaの構図を人間が確認してからWeb実装へ移る。コミット、公開、参照用Figmaの編集は行わない。
