### 3.3 booth 詳細仕様

**構造**
- **個別詳細ページ `/entry/[id]` を持つ**（当初は「詳細ページなし・カード一覧のみで完結」の方針だったが、I科の親子ワークショップのように開催回・対象・定員・注記まで持つ企画が出てきて、カードやhomeのバナーの限られた面積では情報を出しきれなくなったため方針変更）
  - カード一覧・homeのバナーには `summary`（短い要約）だけを出し、「view more」で `/entry/[id]` に送る。長文の `description` と `occurrences` / `audience` / `capacity` / `notes` は詳細ページ側で構造化して表示する
  - 全エントリぶんを `getStaticPaths()` で静的生成する（featured限定にすると、後から特別扱いしたい企画が出るたびにページを手書きすることになるため）
  - 一覧の第1層はあくまでカード。詳細ページは「もっと知りたい人の受け皿」であって、一覧の情報量を減らす言い訳にはしない
- 第1層＝タブ（カテゴリ切り替え）: 出店 / 学科展示 / イベント / ライブ
- 第2層＝タグ絞り込み（複数選択・OR条件）。タブごとに意味の異なるタグセットを表示。**絞り込みバーはスクロール時も画面上部にsticky固定**
  - 出店タブ: 飲食(フード/スイーツ) / レク / 物販 / 展示
  - 学科展示タブ: M科 / E科 / I科 / C科 / S科（1学科あたり約6件、計30件規模）
  - イベントタブ / ライブタブ: 下記`entries/`（結合後のEntry[]）のうち`category`が「イベント」「ライブ」のエントリをカード化（timetableページとデータソース共通）

**データ（`site/src/data/entries/`）**
- 「出店」「学科展示」「イベント」「ライブ」は**同じ型（`Entry`）に統一**する（当初`booths.json`/`timetable.json`の2ファイル案だったが、性質の異なるエントリを無理に2ファイルへ振り分けるより、共通の型で統一した方が扱いやすいため統合。timetableページは、この中から時間軸を持つエントリだけを参照して配置する）
- ただし**物理ファイルは担当ごとに分割**する: `entries/booth.json`（出店）/ `entries/department.json`（学科展示）/ `entries/program.json`（イベント・ライブ）。1本のJSONに統合すると複数人が同時に編集してコンフリクトしやすいため（CLAUDE.mdの「同一ファイルへの同時編集を避ける」）。消費側は`loadEntries.ts`が3ファイルを結合した`Entry[]`を返すので、ページ側は分割を意識しなくてよい
- フィールド:
  - `id` / `category`（出店 / 学科展示 / イベント / ライブ） / `name` / `group`（団体名・学科名・出演者名、任意） / `description`（任意。文字数上限あり、超過分はCSS `line-clamp`で省略。アコーディオン展開はなし）
  - `summary`（任意。バナー等の狭い場所に出す短い要約、40字目安。長文は`description`へ）
  - `tags`（タブごとの第2層タグ。出店:飲食-フード等 / 学科展示:M科等 / イベント:day1,day2,常設 / ライブ:day1,day2,中夜祭,決勝バンド）
  - `location`（テキスト。基本は3.4の7エリア表記、出店のうちエリア③④は詳細位置を追加で持つ。**物理的な場所を持たない企画はnull**）
  - `image`（任意。nullのときの扱いはUIで異なる）
    - **カード系**（BoothList / TimetableList / PromoCard）は「NO IMAGE」プレースホルダーを出してカード高さを揃える。並んだときに高さが揃わないと崩れるため
    - **詳細ページ** `/entry/<id>/` は写真ブロックごと出さない。16:9の空枠がページの14%を占め、情報量ゼロで場所だけ取るため（Issue #56）
  - `occurrences`（**開催の実体を持つ配列**。1件 = 1回の開催で、各件が`day`（`"day1" | "day2"`）＋`start_time`/`end_time`（`"HH:MM"`、未定は`null`）＋`note`（任意。「雨天中止」など回ごとの補足）を持つ）
    - 単発イベント: 1件 / 両日開催: 2件（day1・day2） / 1日に複数公演: その回数ぶん / 出店・学科展示: 日ごとの営業時間を1件ずつ / 常設: 空配列
    - `day`・`start_time`・`end_time`をエントリ直下に1組だけ持つ形からの移行。両日開催（ゲームイベント・化学マジック・I科の親子ワークショップ等）や1日に複数公演ある企画が表現できず、timetableに載せられなかったため
  - `isPermanent`（任意・真偽値。会期中ずっと開催の常設企画。trueのとき`occurrences`は空。以前は`tags`に`"常設"`が含まれるかで判定していたが、タグは表示用の絞り込み語なのでロジックの判定材料にはしない）
  - `audience` / `capacity` / `notes`（任意。参加型企画の対象者・定員・※付きの注意書き。`description`の自由文に埋め込むとUIから構造的に扱えないため個別フィールドにする。`capacity`は「各回10組」のような回単位の表現を許すため文字列）
  - `featured`（任意・真偽値。home等での特別扱い表示の対象かどうか）
  - `link`（任意。外部Webアプリ等へのリンク。コラージュカメラ(仮)用。未提供の間は`null`とし、UIはボタン自体を出さない）
- 並び順: ソートロジックなし。JSON配列の記載順をそのまま表示順とする（委員会側が意図的な掲載順を制御できるようにするため）
- 両日(10/31・11/1)出店が前提。出店・学科展示は片日のみ出店するブースが無いため、営業時間を持つ場合は day1・day2 の2件を同じ時間で並べる（時間未定のあいだは`occurrences`を空配列にしてよい）
- フリーテキスト検索: なし（タブ×タグの絞り込みのみ）
- 表示件数: ページネーションなし。全件1ページ表示 + 画像は`loading="lazy"`
- 更新運用: 非エンジニアの直接編集ではなく、**エンジニアがJSONを編集してpush**する運用（§6参照）

**常設企画「コラージュカメラ(仮)」の特別扱い**
- 概要: お題で指定された物・場所の写真を複数枚撮影し、1枚のフォトコラージュを作るWebアプリ企画。会場内どこでも各自のスマホからアクセス可能（物理スポットに紐づかない）
- テーマ「collage」を体現する目玉企画のため、他の常設企画と同列ではなく**特別扱い**とする:
  - `/booth` 常設セクションの最上部に固定表示。紹介用サンプル画像＋概要文＋Webアプリへのリンクボタンのみ（お題の内容はサイト側に出さず、アプリ内で見せる）
  - home の「PICK UP」枠にも掲載される（3.9参照）。ただし当初想定した「コラージュカメラ専用の横長バナー」ではなく、`featured: true` の企画を並べる汎用枠に一般化した（I科ワークショップなど2件目以降が出たため）
- `entries/program.json`に`category: "イベント"` / `tags: ["常設"]` / `location: null` / `occurrences: []` / `isPermanent: true` / `featured: true`の1エントリとして登録する。他のエントリと型が同じなので、home側もboothの特別カードも同じデータを参照するだけでよく、専用のハードコードは不要

- ベース画像はFigmaでベクター作成中（世界観との整合は別途デザイン検討課題）

- マップの向き（横長維持 or 縦長化）とテキストリストの配置は、レイアウトそのものなのでFigma側で決定する（コードファーストで先に決めない）

- ①LiveStage・②MainStage・⑥SubStageの3エリアには、現在進行中の企画があればタイトルを表示（長い場合は省略）。判定ロジックは3.5のtimetable「NOW」バッジと共通化。⑤ゲームイベント・⑦学科展示は常時開催のため対象外

### 3.5 timetable 詳細仕様

**構造**
- **ステージを横に並べ、時刻を縦軸に取ったグリッド表**（MainStage / LiveStage / SubStage の3列。時間軸は3列で共有する）
- 第1層＝日タブ（Day1 / Day2）。boothと共通のUIコンポーネント（`components/filter/TabTagFilter.tsx`）を流用する。第2層のタグ絞り込みは、ステージが列として常に見えているため設けない
- **載せるのは上記3ステージの企画だけ**。時刻を持っていてもステージ以外で開催する企画（ワークショップ等）は載せない。会場内の特定ステージに紐づかない企画は、トップの pickup や news で扱う
- 「常設」企画はグリッドに混ぜず、日タブ上部に**別枠の常設セクション**として両日共通表示
- 現在時刻に対応する企画には**「NOW」バッジ**を表示（自動スクロールはなし）

**データ**
- 専用の`timetable.json`は作らず、結合後の`entries/`から`lib/entries.ts`の`getScheduledSlots(entries, day)`で行を組み立てる。**表の1行 = 1エントリではなく1 `occurrence`**（`ScheduledSlot = { entry, occurrence }`）。同じ企画でも1日に複数公演あれば、その回数ぶんの行になる（化学マジック等）
- 対象は`category`が「イベント」「ライブ」のエントリの、指定`day`かつ時刻が揃っている`occurrence`。`location`でグルーピングし`start_time`順にソートする（出店・学科展示も`occurrences`に営業時間を持てるが、`category`で除外されるためtimetableには載らない）
- 「常設」セクションは`isPermanent: true`のエントリ（`occurrences`が空で時間軸を持たない）を表示する
- 決勝バンドは`location: "MainStage"` / `occurrences: [{ day: "day2", ... }]` / `tags: ["決勝バンド", "day2"]`（MainStageのDay2セクションに掲載）
- 中夜祭にはバンド以外のイベント企画もあるが、**学外の方は来場できないため現時点ではtimetableの対象外**とする。将来公開する場合は日タブとは別枠を設ける
- 中夜祭は`day1`とは並列の特別枠として扱う。**`occurrences`には実際の日時（day1の夜）をそのまま持たせ**、通常の日タブ（Day1/Day2）からの除外は`tags: ["中夜祭"]`で判定する（`getScheduledSlots`が中夜祭タグを持つエントリを日タブから外す）。以前は`day: null`にして「開催日はあるが日タブに出さない」を表現していたが、データが実際の日時について嘘をつくことになるためやめた。在校生限定・非公開の可能性があるため、公開する場合は`entries/program.json`にエントリを追加するタイミング自体で管理する（専用の公開制御フラグは作らない）
- `/booth`のイベント/ライブタブは、同じ`entries/`を`category`で絞り込んだ上で、`tags`（day1/day2/常設/中夜祭/決勝バンド）を絞り込みタグとして使う

### 3.6 access 詳細仕様

- アクセス手段（電車・バス・徒歩）は§1の情報のまま。埋め込み地図は使わず、外部リンク（Googleマップで開く）ボタンのみ設置
- 駐車場は**主従関係**: メイン＝鈴鹿医療科学大学白子キャンパス、予備＝MEGAドン・キホーテUNY鈴鹿店（立体駐車場3F〜7F、利用時は上の階から順に駐車）。シャトルバスなし
- ドン・キホーテ駐車場への経路案内は、既存の案内資料（暫定素材。後日世界観に合わせて差し替えの可能性あり）を活用する:
  - 経路図（矢印・道路のグラフィック部分）は画像のまま流用し、「貼り付けた紙片」演出（回転+ハードシャドウ、design-system.md参照）で見せる
  - 手順テキスト（①②③④、駐車順序の注意書き等）は画像に埋め込まず、サイト自前のタイポグラフィで打ち直す
- ページに**「最終更新日」を表示**し情報の鮮度を示す（`access.json`に`updated_at`等を保持）

### 3.7 news 詳細仕様

- 基本は「リンク集（ポータル）」。一覧は**タイトルのみ**（日付＋NEWバッジ）で、画像表示は今回見送り（将来必要になったら追加検討）
- リンク先は柔軟に持たせる: 既存ページへのディープリンク（例: 出店一覧公開のお知らせ→`/booth`）が基本。単体で読ませる内容がある場合のみ`/news/[id]`記事ページを生成する
- データは`news.json`1本で管理。個別記事用のMarkdown Content Collectionsは今回作らない（YAGNI。本文が必要な記事が増えたら再検討）
- NEWバッジは**日付からの自動判定**（例: 公開後7日以内は自動表示。閾値は実装時の定数として調整可能）。手動フラグは廃止

**データ（`news.json`）**
```json
{
  "id": "一意のスラッグ",
  "date": "2026-09-15",
  "title": "お知らせタイトル",
  "href": "リンク先（内部ディープリンク or /news/[id]）",
  "body": "Markdown本文（任意。ある場合のみ/news/[id]ページを自動生成）"
}
```

### 3.8 sponsors 詳細仕様

- 法人協賛・個人協賛を**2つのリストに分けて**それぞれ**50音順・名前のみ**で表示（ロゴ・ランク表示なし）
- `featured: true`の高額協賛企業のみ、**フッター（全ページ共通）でロゴを表示**する（§3.1の「主要協賛企業」に対応）

**データ（`sponsors.json`）**
```json
{
  "name": "企業名・個人名",
  "type": "corporate | individual",
  "featured": false,
  "logo": "画像パス or null（featured: trueの場合のみ使用）"
}
```

### 3.9 home「PICK UP」枠 詳細仕様

`featured: true` のエントリを**全件そのまま縦に並べる**。当初は「コラージュカメラ(仮)専用の横長バナー1枚」だったが、I科ワークショップが2件目のfeaturedになったため汎用枠に一般化した。

**見せ方**
- 1行 = 1企画の横長カード（写真小 + ラベル + 企画名 + `summary` + 場所 + `view more →`）
- **行全体が `/entry/[id]` へのリンク**。カード内にCTAリンクを別途置かないので、リンクの入れ子にならずタップ領域が行の全面になる
- カード内の説明は `summary`（40字目安）の1行だけに留め、詳しい内容は詳細ページ `/entry/[id]`（§3.3）に送る
- 実装: `components/sections/FeaturedPromos.astro` + `components/motion/PromoList.tsx`

**切り替えUIを持たない理由**
広告が複数になった際、スタックして切り替える方式（覗いた端をタップ／テープタブ／Apple Wallet型／カルーセル）を4案作って `/gallery` で比較した。結論として**広告は多くても4件程度**であり、畳む必要がないと判断した。畳まないことで「切り替えに2手かかる」「展開すると畳んだ状態より1件あたりの情報が減る」という欠点が両方消える。

**却下した3案のコードは削除済み**（`/gallery` には採用した `PromoList` のみを置く）。判断の根拠は以下に残す。実測タップ領域（375px幅）:

| 案 | 操作対象 | 実測 | 判定 |
|---|---|---|---|
| 覗いた端をタップ | 背面カードの覗いた帯 | 17×452 | WCAG 2.5.8(AA)の最小24pxに届かず却下 |
| テープタブ | タブ | 174×46 / 261×48 | 件数が増えるとタブが折り返して縦に伸びる |
| Apple Wallet型 | 畳んだカード全面 | 287×454 | 2手かかる／展開時は1件あたりの情報が減る |
| カルーセル | 矢印・ドット | 44×44 | コラージュの「重ね貼り」感が失われる |
| **全件表示（採用）** | **行の全面** | **337×143 / 337×186** | — |

**流用**
`entries` と `hrefFor` を受け取るだけで home 専用の前提を持たないため、他ページの広告枠にもそのまま置ける。

## 4. 共通要素

- **背景**: コラージュ（テープや紙が切り貼りされた質感）。実装は design-system.md 参照
- **ヘッダー**:
  - PC（約900px以上）: 左にロゴテキスト、右に7項目横並びnav。hover/現在ページに赤テープ下線（Figmaデザイン準拠）
  - SP: 細い固定バー（左: 小ロゴ、右: ハンバーガー=テープ3枚）→ タップで全画面コラージュメニュー
- **フッター**: home 最下部と同一内容を全ページ共通化

**公開制御（`site/src/data/release.json`）**

段階的に公開するため、「実装が終わっているか」と「利用者に見せてよいか」を分けて管理する。

```jsonc
{
  "mode": "holding",                       // "holding" のあいだ本番は全URLがポスター。v1公開時に "open"
  "published": ["/", "/access/", "/news/"] // 公開する静的ページ
}
```

- `published` に無いページも**ページ自体は生成する**。ヘッダーのnavが全ページから7項目をリンクしているため、消すとトップから飛べる場所が404になる。中身の代わりに「準備中」を出し、`noindex` を付ける
- **`published` を適用するのは一部のビルドだけ**。全ビルドに適用すると、booth担当者が自分のPRのプレビューで自分の変更を確認できなくなる

  | ビルド | `published` | プレビューで見えるもの | E2E |
  |---|---|---|---|
  | 通常のPR | 適用しない | 全ページ（実装中のページも見える） | 全ページ公開を検査 |
  | `release.json` を触るPR | 適用する | 本番と同じ | 振り分けを検査 |
  | 本番（mainへpush） | 適用する | — | 同上 |

  判定は「そのPRが `release.json` を変更しているか」で自動的に行う（`deploy.yml`）。手元では `npm run build:release` で本番と同じビルドを再現できる。E2Eはプレビューと同じモードで走るので、テストが実物を見ていない状態にならない
- `release.json` を触るPRには、公開状態がどう変わるかの表が自動でコメントされる（`scripts/release-diff.mjs`）
- **`published` の初期値は空**。公開するかどうかを決めるのはリリースのPRであって、仕組みを入れるPRではない。空にしておくと `mode` を `open` にしてもいきなり全ページが公開されることはなく、`published` に足したページだけが出る
- 書くのは**セクション単位**（`/news/`）。詳細ページ（`/news/article1/`）は親セクションの公開状態を継承する
- **どの記事・どの企画を出すかは `published` では扱わない**。データ側の `draft` で「そもそも生成しない」ことで制御する（一覧からも消えるためリンク切れが起きない）
- `/gallery`（開発用）・`/holding`（ポスター）・`/404` は判定の対象外
- **開発用ページは本番の成果物から取り除く**（`scripts/strip-dev-pages.mjs`）。`/gallery` は常に、`/holding` は `mode` が `open` になったら削除し、**存在しないURL＝404** にする。「準備中」として残すと、永久に公開されないページを準備中と偽ることになる。PRプレビューでは消さないので開発中はいつでも見られる
- 存在しないURLは `404.astro`（「ページが見つかりません」）を返す。ホールディング中だけはCIがポスターに差し替える
- **sitemap は「本番に実在するURL」だけを載せる**。ホールディング中は実在するのがポスター1枚だけなので `/` のみになる。実体の無いURLを申告し続けると、検索エンジンがクロールしてインデックスに残り、消えたあとも検索結果から飛ばれ続ける（実際に `/booth/` で発生し、5日以上前のキャッシュが表示された）
- 検査は `site/tests/release.spec.ts`。navの7項目が404にならないこと、公開状態と表示が一致すること、sitemapに未公開ページが載らないことを見る
- （検討中）SP画面下固定のクイックバー（map / timetable / booth）— 当日利用のショートカット

## 5. OPムービー（スプラッシュ型）

- 初回訪問時のみ全画面再生。`sessionStorage` で2回目以降スキップ
- `autoplay muted playsinline`（スマホ自動再生の必須条件）
- **スキップボタンを常時表示**（再生開始直後から）
- 再生失敗・reduced-motion・低速回線時はロゴ静止画ヒーローにフォールバック
- 素材: OP.mp4（9.8秒 / 1900×906 / 8.5MB / H.264+AAC）
  - 再エンコード目標: H.264 2〜3MB + 可能なら WebM(VP9/AV1) 併用、SP向け720p版
  - 音声トラックは削除（muted必須のため不要）

## 6. コンテンツ管理（データ駆動）

コンテンツはコードから分離しデータファイル（JSON）で管理する。**更新作業は非エンジニアの実行委員が直接行うのではなく、エンジニアがJSONを編集してpushする運用**とする（当初「非エンジニアでも更新できる形」を想定していたが、実行委員のGit操作は現実的でないため方針転換）。

| データ | 形式 | 更新頻度 |
|---|---|---|
| news | JSON（リンク集ベース。`body`があれば記事ページ自動生成。詳細は3.7） | 開催前〜当日 高 |
| entries/booth.json, entries/department.json, entries/program.json | JSON（出店・学科展示・イベント/ライブを担当ごとに別ファイルで管理し`loadEntries.ts`で結合。boothの全タブとtimetableで共用。詳細は3.3, 3.5） | 確定後ほぼ固定 |
| sponsors.json | JSON（名称・type・featured・logo。詳細は3.8） | 随時追加 |
| access.json | JSON（駐車場情報・`updated_at`。詳細は3.6） | 変更時のみ（高頻度ではないが重要） |

- 更新フロー: GitHub上でエンジニアが編集 → push → Cloudflare Pages 自動ビルド・デプロイ
- スキーマは実データのサンプルをもらってから確定する

## 7. 技術・非機能要件

- **Astro**（静的生成）+ 素のCSS を土台に、インタラクション/アニメーションが必要な箇所のみ React + Framer Motion（`motion`）を「アイランド」として追加（例: ハンバーガーメニュー開閉、セクションのスクロール登場演出）。それ以外のJSは booth 絞り込み・OP制御のみ
- **Cloudflare Pages** にデプロイ（GitHub連携の自動ビルド）
- パフォーマンス: 4G回線で LCP 2.5秒以内を目安。画像は圧縮 + `loading="lazy"`、OPムービーはスプラッシュ以外でプリロードしない
- OGP画像・favicon（ロゴ流用）・タイトル/description 整備
- アクセシビリティ: 文字コントラスト確保、画像alt、reduced-motion 対応（マーキー・OP停止）
