### 3.3 booth 詳細仕様

**構造**
- **個別詳細ページ `/entry/[id]` を持つ**（当初は「詳細ページなし・カード一覧のみで完結」の方針だったが、I科の親子ワークショップのように開催回・対象・定員・注記まで持つ企画が出てきて、カードやhomeのバナーの限られた面積では情報を出しきれなくなったため方針変更）
  - カード一覧・homeのバナーには `summary`（短い要約）だけを出し、「view more」で `/entry/[id]` に送る。長文の `description` と `occurrences` / `audience` / `capacity` / `notes` は詳細ページ側で構造化して表示する
  - 全エントリぶんを `getStaticPaths()` で静的生成する（featured限定にすると、後から特別扱いしたい企画が出るたびにページを手書きすることになるため）
  - 一覧の第1層はあくまでカード。詳細ページは「もっと知りたい人の受け皿」であって、一覧の情報量を減らす言い訳にはしない
- 第1層＝タブ（カテゴリ切り替え）: 出店 / 学科展示 / イベント / ライブ
- 第2層＝タグ絞り込み（複数選択・OR条件）。タブごとに意味の異なるタグセットを表示。**絞り込みバーはスクロール時も画面上部にsticky固定**
  - 出店タブ: 飲食(フード/スイーツ) / レク / 物販 / 展示
  - 学科展示タブ: M科 / E科 / I科 / C科 / S科（1学科あたり約6件、計30件規模）
    - 正式名称は **M=機械工学科 / E=電気電子工学科 / I=電子情報工学科 / C=生物応用化学科 / S=材料工学科**（Issue #53 で確定）
  - イベントタブ / ライブタブ: 下記`entries/`（結合後のEntry[]）のうち`category`が「イベント」「ライブ」のエントリをカード化（timetableページとデータソース共通）

**データ（`site/src/data/entries/`）**
- 「出店」「学科展示」「イベント」「ライブ」は**同じ型（`Entry`）に統一**する（当初`booths.json`/`timetable.json`の2ファイル案だったが、性質の異なるエントリを無理に2ファイルへ振り分けるより、共通の型で統一した方が扱いやすいため統合。timetableページは、この中から時間軸を持つエントリだけを参照して配置する）
- ただし**物理ファイルは担当ごとに分割**する: `entries/booth.json`（出店）/ `entries/department.json`（学科展示）/ `entries/program.json`（イベント・ライブ）。1本のJSONに統合すると複数人が同時に編集してコンフリクトしやすいため（CLAUDE.mdの「同一ファイルへの同時編集を避ける」）。消費側は`loadEntries.ts`が3ファイルを結合した`Entry[]`を返すので、ページ側は分割を意識しなくてよい
- フィールド:
  - `id` / `category`（出店 / 学科展示 / イベント / ライブ） / `name` / `group`（団体名・学科名・出演者名、任意） / `description`（任意。文字数上限あり、超過分はCSS `line-clamp`で省略。アコーディオン展開はなし）
  - `summary`（任意。バナー等の狭い場所に出す短い要約、40字目安。長文は`description`へ）
  - `tags`（タブごとの第2層タグ。出店:飲食-フード等 / 学科展示:M科等 / イベント:day1,day2,常設,中夜祭 / ライブ:day1,day2,中夜祭,野外ライブ）
    - **タグは内部キー。表示名と色は `site/src/lib/tags.ts` の `TAG_META` が唯一の対応表**で、絞り込みバー・カードのチップ・詳細ページのチップがすべてここを引く。表示名を片方だけに置くと、同じ画面でフィルタは「機械」・カードは「M科」と違う言葉が出る（Issue #53）
    - 学科展示のチップは**簡略表記**（機械 / 電気電子 / 電子情報 / 生物応用 / 材料）。横幅の都合による意図的なもので、正式名称は各エントリの `group` が持つ
    - **日付タグ（day1 / day2）はチップに出さない**。すぐ下に「10/31 SAT 11:00-12:00」の時刻行が出るため重複する
    - **日付での絞り込みは `tags` ではなく `occurrences` で判定する**（`matchesTag`）。タグは表示用の絞り込み語であって、開催日という事実の情報源にはしない（`isPermanent` を tags から独立させたのと同じ理由）。データ側で day タグを書き忘れても絞り込みから漏れない
    - チップの色は**タグごとに固定**する。配列の index で振ると、データを並べ替えただけで色が変わる
  - `location`（テキスト。基本は3.4の7エリア表記、出店のうちエリア③④は詳細位置を追加で持つ。**物理的な場所を持たない企画はnull**）
  - `image`（任意。ファイルは `site/src/assets/entries/` に置き、`"/entries/<id>.webp"` のように**先頭スラッシュ付きのパス**で指定する。ビルド時に `lib/entryPhotos.ts` が Astro の画像処理に通し、幅400/800/1200pxの版（srcset）と縦横の寸法を作る。ページ側は `withEntryPhotos` で `photo` を付けてから各部品に渡す。**パスの書き間違い・ファイルの置き忘れはビルドエラーになる**。置く前にWebP化・最大幅1200pxにしておくと、リポジトリが軽く済む。**記事の写真ではなく、リンクから原寸のまま開かせたいファイル（大会ポスター等の `resources`）は `site/public/files/` に置き、`"/files/xxx"` で指定する**（`src/assets/` に置くと最適化用に名前が変わり、そのURLでは開けない）。一覧カード（booth・PICK UP・常設）の写真枠は比率固定の `object-fit: cover`、記事ページは写真の縦横比のまま出す。nullのときの扱いはUIで異なる）
    - **横に並ぶカード**（BoothList / TimetableList）は「NO IMAGE」プレースホルダーを出してカード高さを揃える。並んだときに高さが揃わないと崩れるため
    - **PromoCard**（home の PICK UP / `/booth` の常設セクション）は写真ブロックごと出さない。どちらも縦1列に積むので高さを揃える必要がなく、プレースホルダーを出すと「カードにNO IMAGE→詳細ページには写真領域が無い」という食い違いになるため（Issue #60）
    - **詳細ページ** `/entry/<id>/` は写真ブロックごと出さない。16:9の空枠がページの14%を占め、情報量ゼロで場所だけ取るため（Issue #56）
  - `occurrences`（**開催の実体を持つ配列**。1件 = 1回の開催で、各件が`day`（`"day1" | "day2"`）＋`start_time`/`end_time`（`"HH:MM"`、未定は`null`）＋`note`（任意。「雨天中止」など回ごとの補足）を持つ）
    - 単発イベント: 1件 / 両日開催: 2件（day1・day2） / 1日に複数公演: その回数ぶん / 出店・学科展示: 日ごとの営業時間を1件ずつ / 常設: 空配列
    - `day`・`start_time`・`end_time`をエントリ直下に1組だけ持つ形からの移行。両日開催（ゲームイベント・化学マジック・I科の親子ワークショップ等）や1日に複数公演ある企画が表現できず、timetableに載せられなかったため
  - `isPermanent`（任意・真偽値。会期中ずっと開催の常設企画。trueのとき`occurrences`は空。以前は`tags`に`"常設"`が含まれるかで判定していたが、タグは表示用の絞り込み語なのでロジックの判定材料にはしない）
  - `audience` / `capacity` / `notes`（任意。参加型企画の対象者・定員・※付きの注意書き。`description`の自由文に埋め込むとUIから構造的に扱えないため個別フィールドにする。`capacity`は「各回10組」のような回単位の表現を許すため文字列）
  - `fee`（任意。受講料・参加費。「無料（別途、傷害保険料 50円/人）」のような但し書きを含めて文字列）
  - `application`（任意。事前申込が要る企画の申込先。`url`（外部フォーム）・`opens` / `closes`（"YYYY-MM-DD"、日本時間。締切日はその日の終わりまで）・`guideUrl`（主催側の募集要項ページ））。詳細ページに「申し込む」ボタンと募集期間を出し、受付開始前・締切後はボタンを閉じる。**判定は閲覧時の時刻でも行う**ので、締切後に再デプロイしなくてもボタンは閉じる。`link`とは分けて持つ（`link`は「やってみる」導線で締切の概念が無いため。Issue #96）
  - `featured`（任意・真偽値。home等での特別扱い表示の対象かどうか）
  - `link`（任意。外部Webアプリ等へのリンク。ミッションフォトラリー用。未提供の間は`null`とし、UIはボタン自体を出さない）
- 並び順: ソートロジックなし。JSON配列の記載順をそのまま表示順とする（委員会側が意図的な掲載順を制御できるようにするため）
- 両日(10/31・11/1)出店が前提。出店・学科展示は片日のみ出店するブースが無いため、営業時間を持つ場合は day1・day2 の2件を同じ時間で並べる（時間未定のあいだは`occurrences`を空配列にしてよい）
- フリーテキスト検索: なし（タブ×タグの絞り込みのみ）
- 表示件数: ページネーションなし。全件1ページ表示 + 画像は`loading="lazy"`
- 更新運用: 非エンジニアの直接編集ではなく、**エンジニアがJSONを編集してpush**する運用（§6参照）

**常設企画「ミッションフォトラリー」（旧称：コラージュカメラ(仮)）の特別扱い**
- 概要: お題で指定された物・場所の写真を複数枚撮影し、1枚のフォトコラージュを作るWebアプリ企画。会場内どこでも各自のスマホからアクセス可能（物理スポットに紐づかない）
- テーマ「collage」を体現する目玉企画のため、他の常設企画と同列ではなく**特別扱い**とする:
  - `/booth` 常設セクションの最上部に固定表示。カードは home の PICK UP と同じ `PromoCard` を使い、Webアプリへのリンクボタンだけをカードの外に置く（カード全面が詳細ページへのリンクなので、中に入れるとリンクの入れ子になる）。お題の内容はサイト側に出さず、アプリ内で見せる
  - home の「PICK UP」枠にも掲載される（3.9参照）。ただし当初想定した「コラージュカメラ専用の横長バナー」ではなく、`featured: true` の企画を並べる汎用枠に一般化した（I科ワークショップなど2件目以降が出たため）
- `entries/program.json`に`category: "イベント"` / `tags: ["常設"]` / `location: null` / `occurrences: []` / `isPermanent: true` / `featured: true`の1エントリとして登録する。他のエントリと型が同じなので、home側もboothの特別カードも同じデータを参照するだけでよく、専用のハードコードは不要

### 3.4 map 詳細仕様（booth連携含む）

会場マップは画像+凡例の静止表示ではなく、**エリア単位でタップ可能なインタラクティブマップ**とする。全体MAPには個別ブースのピンを置かない。飲食バザーの詳細図では、屋台の番号から詳細ページへ進める。

**教室配置の正本はGoogle Driveの[教室配置2026.xlsx のコピー.xlsx](https://docs.google.com/spreadsheets/d/1cpnaTE-jhHtYFmtKD7y6n_yUBxeyDOHI/edit)とする（2026-10-08ユーザー指定）。** 企画の棟・階・教室・区画の割り当ては、このExcelを優先する。Figmaや従来の確認記録と異なる場合は差分を記録し、MAP側の対応を正本に合わせる。正本にない入口・経路・区画位置は推測しない。同日の追加確認と更新版Excelにより、校内20企画すべてを教室に対応づけ、`map.json` と `map-indoor.json`、校内図と教室別一覧に反映済み。セル位置と経緯は[校内図の対応表](map-indoor-alignment.md)に記録した。Excel自体は読み取りのみとする。

**校内の教室・区画の並び、仕切り、企画の配置はExcelに合わせる。C科棟とI科棟の向き・位置関係は編集用Figmaを維持する（2026-10-08ユーザー確認）。** Excelのシート上の向きに合わせて棟全体を回転・移動しない。教室配置以外のMAP情報と、紙・色・文字などの見た目は基本的にFigmaを正とする。[参照専用パンフ](https://www.figma.com/design/yHxFTvhmA7nNsLEk4mGdIG/2026?node-id=878-2005)で企画名・番号・会場を確認し、[編集用マップ](https://www.figma.com/design/USj2vcyNX2syrxtzulfnQ6/Untitled?node-id=1005-106)で人間が決めた構成・配置を使う。参照専用ファイルは変更しない。ユーザーから直接訂正された内容はFigmaより優先し、明示的に保留した事項は保留を維持する。既存JSONはIDとデータ構造を再利用するための資料で、Figmaとの相違があればJSONを自動的に優先しない。共有の企画データは変更・削除せず、番号・会場・必要な表示名の差分と掲載対象だけを既存IDに結び付けてMAP側で扱う。紹介文・日時・申込み等は既存データを参照し、企画情報全体は複製しない。MAP以外の変更は極力避け、必要な場合も最小限にする。正本とFigmaから読める情報はAIが確認し、資料にない情報や解消できない矛盾だけをユーザーに確認する。

名称差9件は2026-10-08のユーザー回答で確定した。MAPでは「ベーコンチーズ巻き」「焼きドーナツ」に訂正し、「射的・輪投げ／水泳部」「教員カードゲーム／動画同好会」「シール／5I」は企画名と団体名を分けて表示する。「焼き鳥」「抹茶・栗きんとん」「プロコンプロジェクト」「NEO縁日by@uzumeland」は現在の共有データを維持する。名称・団体名の上書きは `map.json` 内だけで管理し、共有の `booth.json`・`program.json` と詳細ページの表記は変更しない。回答と元の比較は[差分確認資料](map-content-differences.md) §2に記録した。

### 3.5 timetable 詳細仕様

**構造**
- **ステージを横に並べ、時刻を縦軸に取ったグリッド表**（MainStage / LiveStage / SubStage の3列。時間軸は3列で共有する）
- 第1層＝日タブ（Day1 / 中夜祭 / Day2 の時系列順）。1日目は15:00から中夜祭になるので、Day1タブは15:00まで、それ以降は中夜祭タブに出す。boothと共通のUIコンポーネント（`components/filter/TabTagFilter.tsx`）を流用する。第2層のタグ絞り込みは、ステージが列として常に見えているため設けない
- **載せるのは上記3ステージの企画だけ**（中夜祭タブは第一体育館の LiveStage / T字ステージ の2列）。時刻を持っていてもステージ以外で開催する企画（ワークショップ等）は載せない。会場内の特定ステージに紐づかない企画は、トップの pickup や news で扱う
- 「常設」企画はグリッドに混ぜず、グリッドの下に**別枠の常設セクション**として両日共通表示（当日まず見たいのは時刻の表なので、上に置かない）
- 現在時刻に対応する企画には**「NOW」バッジ**を表示（自動スクロールはなし）

**データ**
- 専用の`timetable.json`は作らず、結合後の`entries/`から`lib/entries.ts`の`getScheduledSlots(entries, day)`で行を組み立てる。**表の1行 = 1エントリではなく1 `occurrence`**（`ScheduledSlot = { entry, occurrence }`）。同じ企画でも1日に複数公演あれば、その回数ぶんの行になる（化学マジック等）
- 対象は`category`が「イベント」「ライブ」のエントリの、指定`day`かつ時刻が揃っている`occurrence`。`location`でグルーピングし`start_time`順にソートする（出店・学科展示も`occurrences`に営業時間を持てるが、`category`で除外されるためtimetableには載らない）
- 「常設」セクションは`isPermanent: true`のエントリ（`occurrences`が空で時間軸を持たない）と、`period`を持つエントリを表示する（`getOngoingEntries`）
- バザーグランプリ（投票）・わらしべ長者（物々交換）のように**参加は期間中いつでもできて、結果発表だけステージの時刻に決まっている企画**は、1エントリにまとめて`period`（参加できる期間）を持たせ、発表の回を`occurrences`に`note`（「中間発表」等）付きで入れる。グリッドには「バザーGP 中間発表」のように企画名＋noteで載り、常設セクションにも出る
- timetable に載る企画の記事ページには、下に「前の企画／次の企画」のカードを出す（`EntryNeighbors`）。つながる範囲は**同じタブ（Day1／中夜祭／Day2）× 同じステージ**の並び。来場者は1つのステージに居続けることが多く、知りたいのは「次に何が出るか」なので、日・ステージはまたがない。両日に出る企画は出番ごとに1段ずつ。端の企画はそのステージのタイムテーブルのタブへ戻す。スワイプでのページ送りは iOS の端スワイプ（戻る）や横スクロールとぶつかるので採らない。カードは関連企画（`related`）と共通の横長カード（`EntryLinkCard`）で、SPは縦2段・PCは左に前・右に次の2列
- 企画自体の場所とステージで行う回の場所が違う企画（わらしべ長者は本部テント、結果発表だけ MainStage）は、`location` に企画の場所、その回の`occurrences`に`location`を書く。timetable は回の場所で列を決める（`slotLocation`）
- 当日その場で参加できる企画は`tags`に「当日参加OK」を付け、`participation`に参加方法を書く（出場者を事前募集した企画は「募集は終了しました」と書く）
- 野外ライブ（2日目昼にメインステージ前の野外で演奏するバンド。旧称「決勝バンド」）は`location: "MainStage"` / `occurrences: [{ day: "day2", ... }]` / `tags: ["野外ライブ", "day2"]`（MainStageのDay2セクションに掲載）
- 中夜祭は**在校生限定だが timetable に公開する**（2026-09 判断。当初は学外の方が来場できないため対象外としていた）。一般の来場者が体育館へ向かわないよう、中夜祭タブの先頭に「在校生限定」の注意書きを必ず出す。開場〜入場（`site.json` の `chuyasai.doorsOpen`〜`admissionEnd`）は人が出る枠ではないので企画エントリにはせず、全列にまたがる帯で表示する
- 中夜祭は`day1`とは並列の特別枠として扱う。**`occurrences`には実際の日時（day1の夜）をそのまま持たせ**、通常の日タブ（Day1/Day2）からの除外は`tags: ["中夜祭"]`で判定する（`getScheduledSlots`が中夜祭タグを持つエントリを日タブから外し、`getChuyasaiSlots`が中夜祭タブに集める）。以前は`day: null`にして「開催日はあるが日タブに出さない」を表現していたが、データが実際の日時について嘘をつくことになるためやめた。公開制御は`entries/program.json`にエントリを追加するタイミング自体で行う（専用の公開制御フラグは作らない）
- `/booth`のイベント/ライブタブは、同じ`entries/`を`category`で絞り込んだ上で、`tags`（day1/day2/常設/中夜祭/野外ライブ）を絞り込みタグとして使う。**タグは1つだけ選べる**（OR検索はしない。別のタグを押すと選び直し）。日付タグは`occurrences`で判定するが、中夜祭の企画は日付に含めず「中夜祭」タグでだけ出す（timetableの日タブと同じ`isOutsideDayTabs`）

### 3.7 news 詳細仕様

- 基本は「リンク集（ポータル）」。一覧は**タイトルのみ**（日付＋NEWバッジ）で、画像表示は今回見送り（将来必要になったら追加検討）
- リンク先は柔軟に持たせる: 既存ページへのディープリンク（例: 出店一覧公開のお知らせ→`/booth`）が基本。単体で読ませる内容がある場合のみ`/news/[id]`記事ページを生成する
- データは`news.json`1本で管理。個別記事用のMarkdown Content Collectionsは今回作らない（YAGNI。本文が必要な記事が増えたら再検討）
- NEWバッジは**日付からの自動判定**（例: 公開後7日以内は自動表示。閾値は実装時の定数として調整可能）。手動フラグは廃止

**データ（`news.json`）**
```json
{
  "id": "一意のスラッグ",
  "date": "2026-09-15",
  "title": "お知らせタイトル",
  "href": "リンク先（内部ディープリンク or /news/[id]）",
  "body": "Markdown本文（任意。ある場合のみ/news/[id]ページを自動生成）"
}
```

### 3.8 sponsors 詳細仕様

- 法人協賛・個人協賛を**2つのリストに分けて**表示する
- 並び順は「`featured` → ロゴあり → **協賛金額の高い順**」。ロゴありを先に出すのは、名前だけのスロットが上に並ぶと見栄えが落ちるため
- `featured: true`の高額協賛企業（10万円以上）のみ、**フッター（全ページ共通）でロゴを表示**する（§3.1の「主要協賛企業」に対応）
- 個人協賛が0件のあいだは、空のリストではなく募集中の案内を出す。フッターもロゴが1枚も無いあいだは「主要協賛」のブロックごと出さない

**データ（`sponsors.json`）**
```json
{
  "name": "企業名・個人名",
  "type": "corporate | individual",
  "featured": false,
  "logo": "画像ファイル名 or null"
}
```

> **⚠️ 行の並び順が協賛金額の高い順を表している。**
> 協賛金額は数値としては持たせていない。**このリポジトリは公開されており、各社がいくら出したかは公開情報ではない**ため、金額そのものもその帯もファイルに書かない方針とした。代わりに JSON の行の並び自体を金額の高い順にしてあり、表示側はその添字を使って並べている。
>
> **協賛を追加するときは、末尾ではなく金額に見合った位置に挿し込むこと。** 末尾に足すと最下位の扱いになる。同額のときの順番は問わない（現状は名前順で並べてある）。
>
> 金額の原本はスプレッドシート「協賛企業リターン2026 - 企業」側にあり、リポジトリには持ち込まない。

ロゴ画像の作り方（原本の色空間・余白の揃え方）は [`site/src/assets/sponsors/README.md`](../site/src/assets/sponsors/README.md) を参照。

### 3.9 home「PICK UP」枠 詳細仕様

`featured: true` のエントリを**全件そのまま縦に並べる**。当初は「コラージュカメラ(仮)専用の横長バナー1枚」だったが、I科ワークショップが2件目のfeaturedになったため汎用枠に一般化した。

**見せ方**
- 1行 = 1企画の横長カード（写真小 + ラベル + 企画名 + `summary` + 場所 + `view more →`）
- **行全体が `/entry/[id]` へのリンク**。カード内にCTAリンクを別途置かないので、リンクの入れ子にならずタップ領域が行の全面になる
- カード内の説明は `summary`（40字目安）の1行だけに留め、詳しい内容は詳細ページ `/entry/[id]`（§3.3）に送る
- 実装: `components/sections/FeaturedPromos.astro` + `components/motion/PromoList.tsx`

**切り替えUIを持たない理由**
広告が複数になった際、スタックして切り替える方式（覗いた端をタップ／テープタブ／Apple Wallet型／カルーセル）を4案作って `/gallery` で比較した。結論として**広告は多くても4件程度**であり、畳む必要がないと判断した。畳まないことで「切り替えに2手かかる」「展開すると畳んだ状態より1件あたりの情報が減る」という欠点が両方消える。

**却下した3案のコードは削除済み**（`/gallery` には採用した `PromoList` のみを置く）。判断の根拠は以下に残す。実測タップ領域（375px幅）:

| 案 | 操作対象 | 実測 | 判定 |
|---|---|---|---|
| 覗いた端をタップ | 背面カードの覗いた帯 | 17×452 | WCAG 2.5.8(AA)の最小24pxに届かず却下 |
| テープタブ | タブ | 174×46 / 261×48 | 件数が増えるとタブが折り返して縦に伸びる |
| Apple Wallet型 | 畳んだカード全面 | 287×454 | 2手かかる／展開時は1件あたりの情報が減る |
| カルーセル | 矢印・ドット | 44×44 | コラージュの「重ね貼り」感が失われる |
| **全件表示（採用）** | **行の全面** | **337×143 / 337×186** | — |

**流用**
`entries` と `hrefFor` を受け取るだけで home 専用の前提を持たないため、他ページの広告枠にもそのまま置ける。

## 4. 共通要素

- **背景**: コラージュ（テープや紙が切り貼りされた質感）。実装は design-system.md 参照
- **ヘッダー**:
  - PC（約900px以上）: 左にロゴテキスト、右に7項目横並びnav。hover/現在ページに赤テープ下線（Figmaデザイン準拠）
  - SP: 細い固定バー（左: 小ロゴ、右: ハンバーガー=テープ3枚）→ タップで全画面コラージュメニュー
- **フッター**: home 最下部と同一内容を全ページ共通化

**公開制御（`site/src/data/release.json`）**

段階的に公開するため、「実装が終わっているか」と「利用者に見せてよいか」を分けて管理する。

```jsonc
{
  "mode": "holding",                       // "holding" のあいだ本番は全URLがポスター。v1公開時に "open"
  "published": ["/", "/access/", "/news/"] // 公開する静的ページ
}
```

- `published` に無いページも**ページ自体は生成する**。ヘッダーのnavが全ページから7項目をリンクしているため、消すとトップから飛べる場所が404になる。中身の代わりに「準備中」を出し、`noindex` を付ける
- **`published` を適用するのは一部のビルドだけ**。全ビルドに適用すると、booth担当者が自分のPRのプレビューで自分の変更を確認できなくなる

  | ビルド | `published` | プレビューで見えるもの | E2E |
  |---|---|---|---|
  | 通常のPR | 適用しない | 全ページ（実装中のページも見える） | 全ページ公開を検査 |
  | `release.json` を触るPR | 適用する | 本番と同じ | 振り分けを検査 |
  | 本番（mainへpush） | 適用する | — | 同上 |

  判定は「そのPRが `release.json` を変更しているか」で自動的に行う（`deploy.yml`）。手元では `npm run build:release` で本番と同じビルドを再現できる。E2Eはプレビューと同じモードで走るので、テストが実物を見ていない状態にならない
- `release.json` を触るPRには、公開状態がどう変わるかの表が自動でコメントされる（`scripts/release-diff.mjs`）
- **`published` の初期値は空**。公開するかどうかを決めるのはリリースのPRであって、仕組みを入れるPRではない。空にしておくと `mode` を `open` にしてもいきなり全ページが公開されることはなく、`published` に足したページだけが出る
- 書くのは**セクション単位**（`/news/`）。詳細ページ（`/news/article1/`）は親セクションの公開状態を継承する
- **どの記事・どの企画を出すかは `published` では扱わない**。データ側の `draft` で「そもそも生成しない」ことで制御する（一覧からも消えるためリンク切れが起きない）
- `/gallery`（開発用）・`/holding`（ポスター）・`/404` は判定の対象外
- **開発用ページは本番の成果物から取り除く**（`scripts/strip-dev-pages.mjs`）。`/gallery` は常に、`/holding` は `mode` が `open` になったら削除し、**存在しないURL＝404** にする。「準備中」として残すと、永久に公開されないページを準備中と偽ることになる。PRプレビューでは消さないので開発中はいつでも見られる
- 存在しないURLは `404.astro`（「ページが見つかりません」）を返す。ホールディング中だけはCIがポスターに差し替える
- **sitemap は「本番に実在するURL」だけを載せる**。ホールディング中は実在するのがポスター1枚だけなので `/` のみになる。実体の無いURLを申告し続けると、検索エンジンがクロールしてインデックスに残り、消えたあとも検索結果から飛ばれ続ける（実際に `/booth/` で発生し、5日以上前のキャッシュが表示された）
- 検査は `site/tests/release.spec.ts`。navの7項目が404にならないこと、公開状態と表示が一致すること、sitemapに未公開ページが載らないことを見る
- （検討中）SP画面下固定のクイックバー（map / timetable / booth）— 当日利用のショートカット

## 5. OPムービー（スプラッシュ型）

- 初回訪問時のみ全画面再生。`sessionStorage` で2回目以降スキップ
- `autoplay muted playsinline`（スマホ自動再生の必須条件）
- **スキップボタンを常時表示**（再生開始直後から）
- 再生失敗・reduced-motion・低速回線時はロゴ静止画ヒーローにフォールバック
- 素材: OP.mp4（9.8秒 / 1900×906 / 8.5MB / H.264+AAC）
  - 再エンコード目標: H.264 2〜3MB + 可能なら WebM(VP9/AV1) 併用、SP向け720p版
  - 音声トラックは削除（muted必須のため不要）

## 6. コンテンツ管理（データ駆動）

コンテンツはコードから分離しデータファイル（JSON）で管理する。**更新作業は非エンジニアの実行委員が直接行うのではなく、エンジニアがJSONを編集してpushする運用**とする（当初「非エンジニアでも更新できる形」を想定していたが、実行委員のGit操作は現実的でないため方針転換）。

| データ | 形式 | 更新頻度 |
|---|---|---|
| news | JSON（リンク集ベース。`body`があれば記事ページ自動生成。詳細は3.7） | 開催前〜当日 高 |
| entries/booth.json, entries/department.json, entries/program.json | JSON（出店・学科展示・イベント/ライブを担当ごとに別ファイルで管理し`loadEntries.ts`で結合。boothの全タブとtimetableで共用。詳細は3.3, 3.5） | 確定後ほぼ固定 |
| sponsors.json | JSON（名称・type・featured・logo。詳細は3.8） | 随時追加 |
| access.json | JSON（駐車場情報・`updated_at`。詳細は3.6） | 変更時のみ（高頻度ではないが重要） |

- 更新フロー: GitHub上でエンジニアが編集 → push → Cloudflare Pages 自動ビルド・デプロイ
- スキーマは実データのサンプルをもらってから確定する

## 8. デプロイと配信の運用

**デプロイ**: GitHub Actions でビルドし、`wrangler pages deploy` で Cloudflare Pages に配る。**Cloudflare のビルド環境は使っていない**ので、`CF_PAGES_BRANCH` のような Cloudflare 側のビルド変数は参照できない（必要な値は `deploy.yml` から環境変数で渡す）。

**Cloudflare アカウントは26年度実行委員会のもの**だが、`snct-fes.info` のゾーンは25年度の先輩アカウントにある（§ドメインの経緯）。**キャッシュのパージなどゾーン側の操作は管理者への依頼が必要**。

### キャッシュの扱い

`site/public/_headers` で制御している。

| 対象 | Cache-Control | 差し替え時 |
|---|---|---|
| HTML・`sitemap-*.xml` | `max-age=0, must-revalidate` | **即反映**。パージ不要 |
| `/_astro/*` | `max-age=31536000, immutable` | ファイル名にハッシュが入るので**パージ不要** |
| `ogp.png` / `favicon.*` / `robots.txt` | `max-age=14400`（4時間） | **最大4時間残る**。急ぐならそのファイルだけパージ |

`max-age=14400` は `_headers` に書かれていない。**Cloudflare ダッシュボード側の設定**と思われるので、変更したい場合は管理者に確認すること。

**通常のリリースでパージは不要**。HTMLもsitemapも毎回オリジンに確認しに行く。

### 古いキャッシュは再デプロイでは消えない（実例）

2026-08-19、`_headers` 導入前にキャッシュされた `/booth/` が**5.75日間**配信され続けた。この間 main へのデプロイは**20回以上**成功しているが、**一度も上書きされなかった**。

古いエントリは当時のTTL（`s-maxage=604800` = 7日）で「まだ有効」と判断されるため、キャッシュがオリジンに問い合わせに行かない。**オリジンで404になっていようが、そもそも見に来ないので関係ない。**

- 見分け方: `curl -sI <URL>` で `age` が大きい / `curl "<URL>?cb=$RANDOM"` と結果が違う
- 解決は**パージのみ**。再デプロイ・リリース・ページの作り直しでは直らない
- `_headers` 適用後にキャッシュされたものは `must-revalidate` が効くので、同じ問題は起きない

このとき **sitemap が実体の無い `/booth/` を申告し続けていた**ためGoogleがインデックスし、「鈴鹿高専祭」の検索結果に崩れたページが出た。**sitemap は本番に実在するURLだけを載せること**（§4 公開制御）。
